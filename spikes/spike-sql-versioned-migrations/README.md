# Spike: migrations SQL versionadas por dialeto (MySQL e PostgreSQL)

## Problema

Um padrão comum em projetos PHP pequenos é o próprio endpoint garantir o schema a cada requisição:

```php
$pdo->exec("CREATE TABLE IF NOT EXISTS config (...)");
if (!$pdo->query("SHOW COLUMNS FROM config LIKE 'x'")->fetch()) {
    $pdo->exec("ALTER TABLE config ADD COLUMN x ...");
}
```

Isso traz três problemas:

- **lock e corrida:** duas requisições simultâneas podem tentar o mesmo `ALTER`, e o DDL trava a tabela;
- **privilégio excessivo:** o usuário do banco usado pela aplicação web precisa ter `CREATE`, `ALTER` e `DROP`;
- **acoplamento ao banco:** `SHOW COLUMNS`, `AUTO_INCREMENT` e companhia espalhados pelo código tornam cara a troca de MySQL por PostgreSQL.

## Solução

```
migrations/
├── mysql/
│   ├── 000_create_schema_migrations.sql
│   ├── 001_create_notes.sql
│   └── 002_seed_notes.sql
└── pgsql/                 <- os mesmos passos, no dialeto do PostgreSQL
src/
├── ConnectionFactory.php  <- único lugar que conhece driver e DSN
├── Migrator.php           <- aplica, em ordem, só o que falta
├── NoteRepository.php     <- contrato (Port)
└── PdoNoteRepository.php  <- implementação com SQL portável
migrate.php                <- CLI: status | up
scripts/verify.php         <- prova os cenários contra bancos reais
```

| Peça | Como funciona |
| :--- | :--- |
| `schema_migrations` | Tabela `(version, applied_at)`. A migration `000` a cria com `IF NOT EXISTS`, então ela pode rodar sempre primeiro. |
| `Migrator` | Lê `migrations/<driver>/NNN_*.sql`, compara com `schema_migrations` e aplica só as pendentes, em ordem, registrando cada uma. O diretório é escolhido pelo driver da conexão, sem `if mysql`. |
| Migrations idempotentes | `CREATE TABLE IF NOT EXISTS` com o **schema final** e seeds com `INSERT ... SELECT ... WHERE NOT EXISTS`. Assim a primeira execução em um banco que **já tem** as tabelas (criadas antes do versionamento) apenas registra as versões, sem quebrar nem duplicar dados. |
| `ConnectionFactory` | Monta o DSN a partir de `DB_DRIVER` (`mysql` ou `pgsql`). Nenhum outro arquivo contém DSN ou nome de driver, e o `verify` confere isso. |
| `PdoNoteRepository` | SQL portável (`SELECT id, title FROM notes ORDER BY id`): o mesmo código roda nos dois bancos. |

### Onde os dialetos divergem

| Ponto | MySQL | PostgreSQL |
| :--- | :--- | :--- |
| Chave autoincremental | `INT AUTO_INCREMENT` | `INTEGER GENERATED BY DEFAULT AS IDENTITY` (padrão SQL) |
| `updated_at` automático | `ON UPDATE CURRENT_TIMESTAMP` | não existe: a aplicação atualiza (ou um trigger) |
| `SELECT` com `WHERE` sem tabela | exige `FROM DUAL` | aceita sem `FROM` |
| Engine e charset | `ENGINE=InnoDB DEFAULT CHARSET=utf8mb4` | definidos no banco |

Essas diferenças ficam **só** nos arquivos de migration de cada dialeto. O código PHP não muda.

### O que fica de fora de propósito

- **Rollback (`down`):** em produção pequena, desfazer costuma ser uma nova migration "para frente". O spike não implementa `down`.
- **Transação por migration:** no MySQL, DDL faz commit implícito, então uma transação não protegeria. A garantia vem de cada arquivo ser idempotente.
- **Quem roda as migrations:** um usuário administrativo, via CLI ou phpMyAdmin. O usuário da aplicação web fica só com `SELECT, INSERT, UPDATE, DELETE`.

## Como testar localmente

Requer PHP 7.4+ com `pdo_mysql` e `pdo_pgsql`, e Docker para subir os bancos descartáveis. O `verify` **apaga** as tabelas `notes` e `schema_migrations` do banco informado: use só bancos de teste.

```bash
docker run -d --rm --name spike-mysql -e MYSQL_ROOT_PASSWORD=rootpw -e MYSQL_DATABASE=spike \
  -e MYSQL_USER=spike -e MYSQL_PASSWORD=spikepw -p 127.0.0.1:13306:3306 mysql:8.4
docker run -d --rm --name spike-pg -e POSTGRES_DB=spike -e POSTGRES_USER=spike \
  -e POSTGRES_PASSWORD=spikepw -p 127.0.0.1:15432:5432 postgres:16

export SPIKE_MYSQL_HOST=127.0.0.1 SPIKE_MYSQL_PORT=13306 SPIKE_MYSQL_DB=spike SPIKE_MYSQL_USER=spike SPIKE_MYSQL_PASS=spikepw
export SPIKE_PGSQL_HOST=127.0.0.1 SPIKE_PGSQL_PORT=15432 SPIKE_PGSQL_DB=spike SPIKE_PGSQL_USER=spike SPIKE_PGSQL_PASS=spikepw
php scripts/verify.php

docker stop spike-mysql spike-pg
```

Saída esperada (resumida):

```
✅ PdoNoteRepository.php sem DSN nem nome de driver fixo
— MySQL 8.4 —
✅ banco novo: aplica 000, 001 e 002 em ordem (000, 001, 002)
✅ segunda execução: nada pendente, nada aplicado
✅ tabela pré-existente: dados preservados e seed sem duplicar (Nota antiga | Primeira nota | Segunda nota)
— PostgreSQL 16 —
...
✅ MySQL e PostgreSQL devolvem o mesmo resultado pelo mesmo repositório
```

O CLI de migrations recebe um arquivo de configuração no formato de `config/env.example.php`:

```bash
php migrate.php /caminho/fora/do/repo/meu-banco.php status   # aplicadas e pendentes
php migrate.php /caminho/fora/do/repo/meu-banco.php up       # aplica as pendentes
```

No CI do labs, MySQL 8.4 e PostgreSQL 16 sobem como *service containers* do GitHub Actions, e a saída real do `verify` aparece na página deste spike.
